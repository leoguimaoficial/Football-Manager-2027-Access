# Input System Findings

Empirical results from IL2CPP runtime testing (2026-04-08). These findings supersede speculation in `input-system-history.md` and form the basis for the new input system design.

## The Proven Blocking Mechanism: InputAction.Disable()

`InputAction.Disable()` works in IL2CPP. Tested on 5 navigation actions — all transitioned from `enabled=True` to `enabled=False`. Individual actions can be disabled within a map without affecting other actions in the same map.

`InputAction.Enable()` re-enables them. The game itself uses per-action enable/disable extensively (most of the 49 Navigation map actions are disabled at any given time, toggled by context).

## InputSystemUIInputModule Must Stay Enabled

The current mod disables `InputSystemUIInputModule` entirely at startup. This kills mouse input because UIToolkit pointer events (PointerDown, PointerMove, etc.) are generated by this module. Re-enabling it at runtime restored mouse functionality (confirmed by mouse clicks triggering game UI interactions).

Mouse Point/Click/ScrollWheel actions exist in both the Global map (always enabled) and the Navigation map (contextually disabled by the game). The Global copies provide mouse input to UIInputModule regardless of Navigation map state.

## IL2CPP Property Access

Private serialized fields on game MonoBehaviours are exposed as **properties**, not fields, in IL2CPP. `AccessTools.Field()` returns null; `Type.GetProperty()` with `BindingFlags.NonPublic | BindingFlags.Instance` works. This applies to all `FMNavigationManager` members including action maps, action references, and the UIInputModule reference.

## Submit and Cancel Location

Submit and Cancel are in the **Global** map, not Navigation:
- `Global/Submit`: binds to `*/{Submit}` (platform-specific submit button)
- `Global/Cancel`: binds to `*/{Cancel}`, `<Keyboard>/leftArrow`

The `FMNavigationManager` properties `m_inputActionNavigationSubmit` and `m_inputActionNavigationCancel` are `SIInputActionReference` wrappers that point to these Global actions. Disabling them requires accessing the Global map.

## Navigation Actions Bind to WASD, Not Arrow Keys

The game's keyboard navigation uses WASD:
- `Navigation/NavigateUp`: `<Keyboard>/w`
- `Navigation/NavigateDown`: `<Keyboard>/s`
- `Navigation/NavigateLeft`: `<Keyboard>/a`
- `Navigation/NavigateRight`: `<Keyboard>/d`

Arrow keys are bound to different actions:
- `<Keyboard>/leftArrow`: `Global/Cancel`, `Navigation/Back`
- `<Keyboard>/rightArrow`: `Navigation/Forward`
- `<Keyboard>/upArrow` / `<Keyboard>/downArrow`: `GameWorld/SwitchMessage` (composite)

The mod's `Keyboard.current` polling for arrow keys never conflicted with navigation InputActions. The existing Harmony patches on `OnNavigateUp/Down/Left/Right` were blocking WASD-triggered callbacks, not arrow-triggered ones.

## Key Collision Analysis

Keys that bind to multiple actions across maps:
- `<Keyboard>/space`: Navigation/Continue + Match/TogglePlayPause (different contexts, never both enabled)
- `<Keyboard>/leftArrow`: Global/Cancel + Navigation/Back (both reference Cancel semantics)
- `<Keyboard>/escape`: Navigation/CloseCardPC (only one)
- `<Keyboard>/q`: Navigation/PreviousSubTab (Shift+Q) + Navigation/SwitchPrimaryTabGroup (Q) + Global/ExitApplication (Ctrl+Q) — modifier-differentiated
- `<Keyboard>/p`: GameWorld/Portal + GameWorld/Preferences (Ctrl+P) — modifier-differentiated

No collisions between unmodified letter/number keys across simultaneously-enabled maps.

## Design Implications

1. **Selective disable is the primary blocking mechanism.** `InputAction.Disable()` on claimed actions, `Enable()` when released. No blanket blocking.

2. **InputSystemUIInputModule stays enabled always.** Mouse depends on it.

3. **Handler stack drives enable/disable lifecycle.** Push handler → disable its claimed actions. Pop handler → re-enable them. CapturesAllInput → disable all keyboard-bound actions across all maps.

4. **Reverse lookup at startup.** Scan all bindings, build `keyboard path → List<InputAction>` dictionary. Handlers declare physical keys; the system resolves which actions to disable.

5. **Escape is handler-claimed, not special-cased.** A handler that wants Escape claims it, disabling `Navigation/CloseCardPC`. When that handler pops, the action re-enables and the game handles Escape normally.

6. **Existing Harmony patches on navigation callbacks can be removed** once InputAction.Disable() is the blocking mechanism. The game's callbacks won't fire if the action is disabled. Patches may remain as a temporary safety net during migration.

7. **The `DisableGameNavigation()` method must be removed.** It disables InputSystemUIInputModule, which kills mouse. Replace with selective InputAction disabling.
